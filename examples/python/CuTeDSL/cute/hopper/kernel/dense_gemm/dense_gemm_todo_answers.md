## 核心结论

这个 kernel 的主线是：cluster/block swizzle 选择输出 tile；TMA producer 用 `PipelineTmaAsync` 把 A/B 的 K tile 搬到 staged SMEM；WGMMA consumer 从 SMEM descriptor 发起异步矩阵乘；epilogue 把 RMEM accumulator 转成输出 dtype，先写 SMEM，再用 TMA store 写 GMEM。

阅读这些 TODO 时最关键的几个抽象是：

- `PipelineState.count` 是逻辑 K tile 计数，`PipelineState.index` 是环形 pipeline stage 下标，`phase` 是 mbarrier parity。
- `local_tile(..., proj=...)` 会先按 tiler 做 `zipped_divide`，再用 projection 丢掉某些 GEMM tiler 维度。
- `make_layout_image_mask` 的 "image" 是 layout 的数学 image：固定其他坐标，只枚举某一维，得到要 multicast 到的 CTA rank bitmask。
- `tiled_mma` 是整个 warpgroup MMA 的全局描述；`thr_mma = tiled_mma.get_slice(...)` 是某个 warpgroup/thread-slice 视角下的 partitioner。
- WGMMA 是异步提交模型：`fence -> gemm -> commit_group -> wait_group` 控制 operand 可见性、提交边界和 outstanding group 数。

| 1226 | epilogue 为什么不直接写 global，而要先写 SMEM | 因为当前 epilogue 选择 TMA store，而 TMA store 的数据路径是 SMEM -> GMEM，不能直接从 RMEM accumulator 写 GMEM。于是 accumulator 先通过 `stmatrix`/R2S copy 写入 SMEM 的 epilogue tile，再由 `CopyBulkTensorTileS2GOp` 写回 GMEM。直接 RMEM -> GMEM 也可做，但那是 SIMT/vector store 方案，不是这个示例的 TMA store 方案。 |
| 1245 | epilogue 能否和下一阶段 overlap | 在单个 CTA tile 内可以部分 overlap：`epi_stage`、`epi_buffer = epi_idx % stages` 和 `PipelineTmaStore` 允许上一 epilogue subtile 的 TMA store 在飞时，当前线程准备下一 subtile 的 RMEM->SMEM。跨输出 tile 的 overlap 在这个普通 dense kernel 中基本没有，因为一个 CTA 只做一个 tile 后退出；persistent 版本有循环取下一个 tile，但当前结构仍在每个 tile epilogue 内做必要同步，并没有把下一 tile mainloop 与上一 tile store 深度流水化。 |
| 1254 | 为什么选 `StMatrix8x8x16bOp` | Hopper 的 `stmatrix` 是 warp-level RMEM->SMEM store 指令。`StMatrix8x8x16bOp(..., 4)` 对应 16-bit 输出的 8x8、x4 store atom，适合把 WGMMA C layout 的 accumulator fragment 高效写成 TMA store 期望的 SMEM tile。`hopper_helpers.get_smem_store_op` 对 16-bit 输出也选择这个 atom；非 16-bit 输出会走 `CopyUniversalOp`，所以这里硬编码的 `copy_atom_C` 主要服务 16-bit epilogue layout，需要注意它对 8-bit/32-bit C 的适配边界。 |
| 1266 | tiled copy 不同类型代表什么 | `make_tiled_copy_C_atom(copy_atom, tiled_mma)`：按 MMA 的 C TV layout 构造最小 C-layout copy atom；`make_tiled_copy_S(copy_atom_r2s, tiled_copy_C_Atom)`：用实际 R2S copy atom，并匹配前一个 tiled copy 的 source layout；`make_tiled_copy_D` 则是匹配 destination layout。A/B/C/S/D 后缀本质是在说 tiled copy 的 thread-value layout 要对齐哪一侧或哪类 operand 的 layout。 |
| 1270 | `get_slice(tidx)` 如何得到对应 SMEM 分区 | `tiled_copy_r2s.get_slice(tidx)` 返回当前 thread 的 `ThrCopy`，里面保存 `thr_idx`。后续 `partition_D(sC)` 调用 `tiled_copy_partition_D`，按 tiled copy 的 thread-value layout 和 tiler，把 SMEM destination 切成该线程负责写的元素集合；`retile(accumulators)` 则把 accumulator RMEM 视图重排成同一 copy atom 的 source 视图。 |
| 1326 | dtype 转换为什么需要两个寄存器 tensor | `tRS_rD` 的 element type 是 accumulator dtype，`tRS_rD_out` 的 element type 是 output `c_dtype`。`acc_vec.to(self.c_dtype)` 产生的是转换后的值，需要存进一个 c_dtype 的 RMEM tensor，后续 R2S copy atom 也按 c_dtype 解释 source。这里主要是类型不同导致需要两个 SSA/register view，不一定表示物理上一定多一整份长期寄存器；编译器可做生命周期优化，但在 DSL 层必须显式表达转换前后两个 typed tensor。 |

## 可继续验证的点

- L2 swizzle 的收益必须 profile，建议比较 `group_size_m=1/2/4/8` 或 persistent 版本的 `--swizzle_size`，观察 L2 hit/sector 与整体 TFLOP/s。
- `copy_atom_C = StMatrix8x8x16bOp(..., self.c_dtype)` 对非 16-bit C dtype 的覆盖范围值得单独跑测试；`copy_atom_r2s` 已有 fallback，但 `copy_atom_C` 仍硬编码 16b atom。
- 如果要把 `k_pipe_mmas` 调大，必须同步调整 prologue count、tail release、`wait_group(k)`、`ab_stage` 约束，并用小 K 边界 case 验证。
